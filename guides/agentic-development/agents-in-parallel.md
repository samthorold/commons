# Agentic development Guide: agents in parallel

The Conventions for launching, briefing and cleaning up after agents, and for a sub-agent's hand-back, from [the Agentic development Guide](../agentic-development.md#agents-in-parallel), which says when to read them.

- **One git worktree and one branch per agent.** Independent slices run concurrently; their merges still happen one at a time, each PR catching up with `main` as in [catching up with `main`](catching-up-with-main.md).
- **Each brief carries the workflow rules of [the PR workflow](../agentic-development.md#the-pr-workflow)**, conflict resolution included. A sub-agent sees only its brief and the Imported Guides, not the conversation that launched it. A brief also names the Guides' detail files that its job triggers, where the launcher knows the job (a re-recording issue gets the Model calls Guide's `changing-an-act.md`): the when-lines reach a sub-agent through its Imports, but naming the file costs nothing. A brief for an agent that writes about the owner says to call them "the owner" or they/them: unbriefed, sub-agents write he/him.
- **An act gated on the owner's say (an expensive run, a spend) is granted in the brief**, with its cap, before launch. If the need appears mid-run, whoever launched the agent runs the act itself. *Why:* a sub-agent rightly treats a message from another agent as direction, never as the owner's consent, so consent relayed mid-run stops it short.
- **Ignore the worktrees directory** (e.g. `.claude/worktrees/`) in `.gitignore`, so a `git add -A` in the primary checkout can't stage the worktrees as embedded repositories.
- **Whoever launched an agent removes its worktree and branches** once the agent's work has merged or been abandoned, and only after every completion notification (*a delegated agent can outlive its hand-back*, in [the Guide's Known traps](../agentic-development.md#known-traps)): the worktree, any branch the harness made for it, and its work branch if the merge didn't delete it. Delete a branch only once its work is on `main`. A squash merge doesn't make a branch's commits ancestors of `main`, so `git branch -d` refusing one means checking that its PR merged, not forcing it. Entries whose folders are already gone are cleared with `git worktree prune`. *Why:* the harness leaves them behind, so every run adds branches and dangling worktree entries. A later agent reading `git branch` then can't tell leftovers from unmerged work.
- **Each worktree builds its own environment** (virtualenv, compiled artefacts), from shared caches. On a small machine, cap build and test parallelism per agent so several agents fit at once, and cap the number of agents by what the full check costs, not only by memory: a per-agent cap doesn't limit how many agents' heaviest test runs overlap, and contention alone can push them past the test runner's timeout. A timeout whose running test had started only seconds before is load, not a hang: re-run it alone with a longer timeout, or leave it to CI. Shared state still collides: a `git fetch` can fail on a ref lock held by another agent's fetch, and some tools refuse to start while another instance runs, across worktrees too. Briefs say to retry these rather than diagnose them.
- **Slices that touch the same files** (lock files, a shared results document, a CLI entry point) are fine to run in parallel: the later PR merges `main` in and resolves. Sequence them only when one slice's design depends on another's outcome, or when both regenerate a file that can't be merged hunk by hunk, only generated again (an Archetype's Guide names such files, e.g. recorded model runs).
- **A PR holds the change its slice asked for.** When a delegated slice comes back needing more, a fix to what it was asked goes back to it on the same PR; anything further is its own slice, even when the same agent does it, and what is done and sound merges first. *Why:* each extra change sent back on the same PR makes it harder to review and its outcome harder to attribute, and a send-back is the orchestrator's easiest move.
- **A sub-agent drafts follow-up issues and reports them; whoever launched it opens them**, as with Lessons (Global Guide, *Lessons*). Likewise a sub-agent whose product is a document (a research report) returns it as its final message, and whoever launched it saves it. *Why:* a follow-up an agent decides on is recorded where the next reader looks (*decide, record, carry on*), but a sub-agent's permissions may not reach the tracker or the document's home, and parallel agents would open duplicates. Saving it also gives the launcher a point to fix it (house style, pronouns, links) before it lands.
