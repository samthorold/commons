# Agentic development Guide: catching up with `main`

The Conventions for a branch catching up with `main` and resolving conflicts, from [the Agentic development Guide](../agentic-development.md#the-pr-workflow), which says when to read them.

- A PR that falls behind `main`: merge `main` into it, never rebase (`gh pr update-branch <n>`, or `git merge origin/main` when it conflicts), then wait for CI again. With squash merges the branch history never reaches `main`, so rebasing buys nothing; a merge resolves conflicts once, in one commit `git show` exposes, with no force-push.
- Resolve conflicts hunk by hunk, never by taking one side of a whole file, and before pushing check that `git diff origin/main --stat` lists only the PR's own changes. *Why:* a resolution that takes one side of a file silently deletes another PR's merged work, and CI stays green because the deleted tests go with the deleted code. A deletion outside the PR's scope means a resolution went wrong. Fetch and merge `origin/main` immediately before the check: worktrees share one repository, so another agent's fetch moves `origin/main` under you, and work merged since your last merge then shows as deletions in yours.
- After resolving a conflict in prose, read the resolved region through, and check that `git diff origin/main -- <file>` removes or changes none of `main`'s headings. *Why:* where both sides appended at the same place (a results log parallel agents add to), git can line up text the additions share and cut the conflict in the wrong place, splitting a heading across the blocks; keeping both sides in order then leaves a fragment mid-section, and the `--stat` check can't see it because the files and line counts look right.
