# Model calls Guide

**Scope:** Archetype = apps whose acts call a language model, any Stack. An **act** is a piece of the app's work done by a model call: its instructions, the input it is shown, the output schema it answers in and the checks its output must pass before anything is written back. An app is in this Archetype when behaviour that matters comes from a model's judgement at run time. Like an emergent system's, that behaviour is observed by running it, not derived from the code; unlike one, it comes from a component the project neither owns nor can inspect, and every run of it costs money.

Code around an act (parsing, checks, storage, the loop that drives a conversation) is ordinary code under the Agentic development Guide's test-first Stance. This Guide says how that Stance applies to the act itself, and how the act's inputs are shaped. How hypotheses about the end state are declared and read is the Project knowledge Guide's end-state Stance.

## Stance: models sit behind a port, and are chosen by measurement

- **Stance:** each act calls a provider-neutral port (one call, a batch, a conversation turn), and the provider's SDK and types stay inside its adapter. The model each act runs on is config, chosen per act by measuring candidates on the act's own fixtures, not by reputation.
- **Why:** models change faster than the app: new versions ship, prices move, and one act's best model isn't another's. An act that knows its provider can't be measured against another one. The agent advising on the choice is itself one vendor's model, and a vendor-specific skill may supply that vendor's prices and defaults. Its framing then drifts toward that vendor (comparisons within one line-up, recalled terms presented as fact), and nothing in the conversation corrects it.
- **How to apply:** research the options from sources (Project knowledge Guide, *domain claims come from sources*), with a brief that names no vendor and asks for even-handedness, and put several vendors on the shortlist, open-weight and closed. One adapter is fine while measurement favours one provider: the port is what keeps the choice open. Pin the model version an act runs on, so a provider's silent upgrade can't change behaviour between two readings.
  - **Pin the request, not only the model.** Set every option that changes what the act does or costs (thinking on or off, its effort) explicitly, chosen by measurement like the model: a request that relies on the provider's defaults changes when they do. Size the output bound from the usage the provider reports, thinking included, not from the visible answer: on a model that thinks by default, thinking can fill most of the bound and cut off long inputs while the answer looks short.
  - **A pin fixes the weights, not the serving around them.** Providers can change routing, classifiers or sampling under a fixed model ID, so recordings replaying green don't show that behaviour in use is unchanged; the reading in use (tier 3) is what can. Keep with each result the model the provider reports, not the configured string, so a moved alias shows in the store.
  - **A candidate model is recorded off the pin.** The recording harness records a candidate into a scratch directory without changing the pin, hashing each request with the model being recorded. Where fixtures are chained, the measurement's brief chooses a basis and says which: each fixture over what the pinned model left (the same requests bar the model, one difference at a time), or over the candidate's own chain (how differences compound, on different requests). Where the app keeps its judgements, a candidate can also be measured on a sample of the live record (*every call in use is kept, and a changed judge judges forward*).
- **What would change our mind:** an act that depends on a feature only one provider has, where the port would have to pretend otherwise. The act then names the provider in the design, and says why.

## Stance: three tiers, and the suite never pays for a call

- **Stance:** an act is tested in three tiers.
  1. **A fake model, injected at the port**, for everything around the call: typed results, the checks before anything is written back, tracing, errors and retries. Fast, deterministic, written test-first.
  2. **Recorded runs**: the real model is called on committed fixtures, its responses are kept, and the suite replays them, judging properties of the outputs (never exact text). Only recording costs money; it is done deliberately, never by the suite.
  3. **Judgement quality is a hypothesis**, read in use (from the owner's feedback, say), not something CI asserts.
- **Why:** a suite that calls a model is slow, costs money on every run and isn't deterministic, so it stops being run. A suite that only fakes the model never sees what a real one does with the instructions. Asserting exact text breaks on every re-recording without saying anything about whether the act works.
- **How to apply:**
  - Fixtures are material the repo may hold. Material the app may read but not store or redistribute can't be a committed fixture.
  - Make fixtures by the production path (the same collection, the same truncation), or check that they match it. A fixture richer than what production collects lets a property pass on input the model is never given in use, and nothing fails to say so.
  - A property that relies on a case appearing (a reaction, a piece of feedback) names the fixture it needs, hand-made from admissible material, and asserts that the case is present, in a test of its own over the act's inputs (fixtures and frozen copies). Otherwise a re-recording or a refreshed input that drops the case leaves the property testing nothing, and an assertion that runs only inside the replay never runs while the recordings are stale, so the loss shows only on a paid run.
  - **A property tied to a case reads only that case's output.** It names the output it rests on (the item drawn from the reaction, not everything drawn from the input), asserts it is present, and checks only it; everything else the input yields is free to vary. A property worded over the whole fixture is refuted when an upstream change rightly draws a second item from the same input, and narrowing it after the reading looks like moving the line: it is a fix only with the evidence that the failure came from another output, shown in the PR.
  - **Selection is not classification.** "Drawn as X" fails two ways: drawn as something else, or not drawn at all. A property says which it tests, and a classification property ("when drawn, it is X") sits beside a selection property, never in its place. A change that widens or narrows a category in the instructions moves selection too (newly counted items crowd out what used to be drawn), so its paired report is read for what each fixture draws, not only for the category.
  - **Assert judgement, not wording.** A property that is a list of words (no statement contains *will*) tests wording: the model meets it with synonyms, and it catches legitimate uses. Assert the property on the cases the standard is about, by meaning, and report word counts in the paired report rather than asserting them. Never put a property's own words into the act's instructions: it teaches the model to swap words.
  - **A property's helper reads only the field the property is about.** A helper that also searches what is tied to the output (names linked to a statement) passes on text the output never held. A change that removes a bridge or a derived field checks every helper that reads it, since a replay stays green either way.
- **What would change our mind:** models cheap and deterministic enough to call in the suite, which would make tier 2 a live test.

## Stance: a recording answers exactly one request

- **Stance:** a recording answers the request it was made for, exactly as it was sent, and the replay fails as stale when the code would now send any other.
- **Why:** a replay that doesn't compare the request the code would send now stays green after the instructions, schema or model change, testing a prompt that no longer exists. And a sample is only a sample of the act if it answers the same request as the others: one drawn over a different prior state, or lost to the provider, measures something else.
- **How to apply:**
  - Keep a hash of the request as sent (instructions, schema, input, model, and in a conversation the model's earlier turns in the form the provider returned them) with each recording, and keep in the recording whatever is needed to rebuild it. Fail the replay as stale on a mismatch. Fail, don't skip: a skipped property quietly tests nothing.
  - Acts that feed each other (one act's output is the next one's input) record in sequence and stop at the first failure. Otherwise one failed call moves every later call onto a request no recording holds.
  - Fixtures that build on each other (each one's work changes the state the next is run over) carry each earlier fixture forward by one sample chosen before its results are seen (its first), and every sample of a later fixture runs over a copy of that state. Otherwise each sample answers a different request.
  - A call that brings back no answer while recording (a transport error, the provider overloaded) is not a sample: retry it, or stop without keeping it. An answer that came back counts, even one returned as an error (the model refusing, an answer cut off), since that is the act's behaviour on its request.
  - Write each recording as soon as it arrives, or check its destination before the first call: a harness that writes only at the end loses a paid run when the write fails.
  - A recording of a tool-using act keeps, beside each turn, what the tools returned and the outcome (continued, refused with the reason told back, applied). The replay doesn't need it; whoever compares two recordings does.
- **What would change our mind:** nothing foreseeable. A request either is the one the code sends or it isn't.

## Stance: an act is judged over its samples, in the suite

- **Stance:** a recording is one sample of a stochastic act. Each fixture is sampled N times, every sample is kept, and the suite replays them all and judges each property per fixture by a rule declared before the samples were drawn, on every run.
- **Why:** a property passing on one sample says little about its pass rate: a recording that happened to pass hides a flaky property until the next re-recording exposes it. A rate judged once at recording time is a claim in a PR body that nothing checks again; a later change to how a property is asserted quietly stops testing the samples it was measured on. Derived on every run, the status stays true of the code, as a register's does (Project knowledge Guide, end-state Stance). Pooled across fixtures, a rate hides a property that fails on one input.
- **How to apply:**
  - Declare N and each property's rule (supported, refuted, undecided, by count) before the samples are drawn, as reading rules are declared.
  - A sample is one piece of work run as it runs in use, with the act's retry budget. Passing the act's own checks is rated over all samples ("passes within its attempts": a refused try costs a retry, not a wrong output). A property only the suite asserts runs nowhere in use, so it is rated over the samples that passed their checks.
  - A re-recording reads its failures by where they fall. The same fixture failing the same check on every try is a regression. On a large share of tries but not all, it is a slip: a defect in the act, paid for as a retry every time it happens in use. Different fixtures failing on different tries is flake. Only flake is answered by drawing again.
  - **Rest each use on the judgement reliable enough for it.** When an act's output varies between samples, first ask what rests on it, before tightening the instructions. Where several uses read one act's output, each rests on the most reliable judgement that serves it, by what a miss costs there: a candidate search can rest on what a text names (among the most reliably judged), while a link shown to the owner, where a false tie misleads, needs the judgement it shows. The variation then decides only what costs least to get wrong. A wider candidate set needs a bound to keep each call's cost flat.
  - Redrawing a fixture re-reads every property it has. A slip, or any property refuted or undecided that the run wasn't aimed at, stops the run and is reported, never redrawn: drawing until a count crosses its line is not a reading. The fix is a change to the act (*change an act on its cheapest stage*). A slice that redraws one fixture for a narrow reason counts the cost of re-reading all of it when it is sized.
  - A change to an act's instructions, schema or model reports its samples beside the current version's, per fixture and with every output field counted, next to the rule's verdict. The pairing removes the variance between fixtures, and shows side effects no pass-rate line catches. It is a report for whoever accepts the change, not a second rule: a suite this small detects only large differences (Miller 2024, *Adding Error Bars to Evals*, arXiv:2411.00640).
- **What would change our mind:** an act whose output is deterministic for a fixed request (temperature zero, a provider that guarantees it), where one sample is a verdict.

## Stance: change an act on its cheapest stage, then record the chain once

- **Stance:** an act's instructions or schema change in a loop on that act alone, recorded over frozen copies of what it rests on, until its samples meet a criterion declared before they were drawn. Only then are the acts that build on it brought onto its new output, together and once: a **refresh**.
- **Why:** re-recording cascades. A change to one act makes every downstream act's recordings stale, so its real cost is the whole chain's. Problems in a changed act are visible in its own output, and re-recording the chain for each fix pays the cascade every time.
- **How to apply:**
  - **Each act is recorded over its own frozen copies** of the upstream recordings, never over the upstream recordings themselves, so re-recording one act leaves every other act's recordings valid. Copies, not hand-made input: they were made by the production path, and hand-made input lets a downstream act pass on what no upstream act writes. A frozen copy is part of the downstream act's request, so it goes in the request hash. It is loaded as it was kept, not passed through the upstream act's current checks: the act that made it checked it then, and re-checking it would make a new upstream check fail acts it never touched.
  - **A refresh is a change of its own**, made after the upstream change is accepted. It copies every upstream act's recordings together, since new output from one beside old output from another is a run no production pipeline makes, and goes in chain order, since each act's recordings answer its own copies.
  - **Two checks cover the gap until a refresh**, with no recording of their own. A chain replay over the most downstream act's frozen copies, one consistent run, asserts only properties that span acts (an output traced back to its source). A compatibility check feeds each act's current recordings to the acts downstream on a fake model, so a change in the shape of an upstream output fails at once. A change in what an upstream act judges is not a code failure; the refresh brings it downstream.
  - **Frozen copies stop only what stays inside one act's output.** Anything that renders an upstream answer into a downstream request crosses them: vocabulary the acts share (a label renamed, and rewritten in the copies as a migration rewrites stored rows, still changes what a downstream act is shown), and plain code (a quote matcher fixed to match whole words moved quotes in the copies, and five acts went stale). It is the chain's case of *what shared code builds for an act is its input*. Before any spend, make the change and run the replay suite with no model to see which acts go stale; the brief then budgets their re-records, the expensive ones with the owner's say up front.
  - **A check belongs to the act that owns its standard.** A downstream check that re-judges what an upstream act decided turns every sample-to-sample variation upstream into a downstream refusal, read as the downstream act failing. Such a check is the upstream act's own, or a sign the downstream act should own the decision.
  - **Probe before sampling.** Before drawing a fixture's N samples, draw one and check that the case its property rests on reaches the act at all: a probe costs cents, and finds an input that never exercises the property, a precedent that doesn't carry, or a first try the act's retry must cover. The recording harness can draw a single sample on request.
  - Change one thing per recording. Two prompt changes and a schema change in one recording can't say which did what.
  - **The owner's say gates expense, not each change.** A slice that changes an act merges on a criterion declared when the slice is written, before it records (every property supported by its rule, plus any refutation it declares), read by the agent. A slip's fix is such a slice: its criterion is the slipped property supported. Its review cases and the paired report go in the PR body, for the owner to read without blocking the merge. The owner's say gates the first step where being wrong gets expensive (a chain refresh beyond what the brief grants, a run on an expensive model, a release). A later slice waits on the owner's verdict on an earlier one only when its design, not just its recordings, depends on it. *Why:* holding every change to an act for the owner fights agents that can act and judge on their own (Agentic development Guide, *decide, record, carry on*); a criterion declared up front is the owner's judgement made in advance.
  - "Re-record once the instructions settle" is not a ready criterion: it depends on behaviour nobody has seen yet. Split it into a slice that changes the act, with its declared criterion, and a slice that refreshes the chain. An acceptance only the owner can judge gets a checkable criterion in the grill that writes the slice; holding the slice for the owner is the fallback.
  - Slices that re-record the same recordings run in sequence. A conflict in a recording can't be resolved hunk by hunk, only recorded again, and that costs money.
  - Every brief that re-records says which recordings, the retry budget per fixture and the most it may spend. A run on an expensive model needs the owner's say.
- **What would change our mind:** recordings cheap enough that the cascade costs nothing worth planning around.

## Stance: everything the model is shown is part of its instructions

- **Stance:** the act's standard is stated once, in its own instructions, and every check its output must pass is a standard the instructions state. Whatever else reaches the model (precedents, schema descriptions, the order and placing of the schema's fields, framing text around the input, what its tools return) is treated as instructions too, and is changed and recorded as deliberately as they are.
- **Why:** a model takes everything in its context as guidance. Text added for one feature shifts its judgement on every input, and so does text taken away, on properties with no apparent bearing on it: that is editing the instructions by another route, and nothing in the instructions' diff shows it. The mirror holds too: a check the model isn't shown is a standard it can't meet, so it fails it the same way on every try, and in use the work fails every attempt.
- **How to apply:**
  - **A rule earns its place by an output.** Before adding a rule to an act's instructions, name the output the end state reads that it changes, and the part of the end state that reading serves. If there is none, the instructions say nothing, and the case is left to feedback and its precedents. Inconsistency the recordings show is not a reason on its own: every rule shifts judgement on every input, so one that changes nothing read is cost with no return.
  - **Removing text is changing the instructions.** A slice that takes text out of an act's instructions samples every property of the act, not only those about what was removed, and budgets for an instructions fix. The free stale check says which recordings a change touches, never which properties still hold.
  - **A new check is a new standard.** A slice that adds a check on an act's output sends the same request, but changes what the act must produce. Before it is ready, run the check over the existing recordings (free) and a few fresh samples. A refusal there is a false failure or a standard the instructions never stated; if the latter, the slice changes the instructions too, on the act alone (*change an act on its cheapest stage*).
  - **Words near a field's name fill the field.** Instructions describing a concept in words close to an output field's name act as instructions for that field (a paragraph saying an entity is involved "when it has a role" filled an optional `role` field on nearly every mention). Where a field must stay narrow and the instructions need nearby concepts, enforce its scope in code (drop the value where it doesn't apply) rather than by more wording: code leaves the request, and every recording, unchanged.
  - **Rewording that doesn't converge is a signal to zoom out.** When successive wordings of an act trade one failure for another, look higher before the next wording: a glossary term used for two things, a relation with no term, a category with no source (Project knowledge Guide, *domain claims come from sources*). A category's name is shown to the model and the owner, so its connotations are part of its definition: an *affected* role reads as harm. Use the neutral term the sources use.
  - **What shared code builds for an act is its input.** What a tool returns, or the query that assembles an act's input, often lives far from the act (a storage query a tool shares with a page). A change made for the page changes what the act is shown and can make its recordings stale, carrying the act's re-record cost inside what looks like a storage or UI change. Name beside each act the queries its input and tools read, and brief a slice that changes one to run the act's replay and stop for the owner's say if it goes stale.
  - **A precedent is a case, not a rule.** Past feedback shown as precedent comes with explanatory text only when there are precedents to show, and that text restates no rule. An input with no precedents is then processed exactly as it would be without the feature. A standing paragraph explaining what counts as an error, shown even when no precedent is, shifts the model's judgement everywhere. Feedback ages by kind: feedback on what the owner wants (missed, unwanted) drifts with their taste, so as precedent it weighs less the older it is; feedback that a judgement is wrong holds at any age.
  - **Whether a precedent carries is a hypothesis.** One piece of feedback shown as precedent may not change the judgement even on the case it was given on, above all on a small model. Record each act's precedent case on that case judged again first. An act whose own case doesn't hold by the declared rule is shown no precedents, since it can't be said to follow them. Whether a precedent carries to cases merely like it is read in use, not assumed.
  - **Schema order is generation order.** A model writing structured output tends to write the fields in schema order, so set the order deliberately: what is referred to comes before what refers to it. A schema built from an unordered type is serialized in an order the design never chose (a Go `map[string]any` marshals its keys alphabetically); build it with an ordered type, or shape it so order can't matter (inline the referenced objects instead of referring to them by name).
  - **Ask for a judgement where it is used.** A per-item judgement asked for in a separate list, apart from the element that uses it, is often skipped. Ask for it inside that element, and put a short note field before free prose that must respect it (who speaks the quoted words, before the sentence telling them).
- **What would change our mind:** models whose judgement is demonstrably insensitive to such context, measured on the act's own fixtures.

## Stance: the model judges addresses into the source, and never rewords it

- **Stance:** an act that works on source text is shown it cut into numbered stretches by plain code, and cites stretches by number (finer ones as words quoted within a numbered one, which code turns into an address). Each judgement (what a stretch refers to, who speaks it, what it names) is kept apart from the text, addressing it. The source's words are never rewritten by a model.
- **Why:** a model asked to extract propositions rewords them, and every rewording makes judgements of its own that nobody asked for and nothing records: it resolves references ("the city" becomes Derby), invents attributions (the speaker of one sentence becomes the subject of the next), and drops the speaker's voice (a quoted view comes out in the app's own). Every later act then builds on text the source never wrote. Judged by address, each of those becomes a judgement of its own, checkable and open to feedback; tracing becomes a property of the address, not a quote check; and since the text never changes, no later judgement or feedback is left pointing at something reworded.
- **How to apply:**
  - Numbers, not offsets: models cite numbers reliably and character offsets poorly.
  - Code turns quoted words into an address by matching them as a reader sees them (curled quotes as straight, markup dropped) and only as whole words ("he" inside "The" has no address), and the act's checks refuse a number not shown or words not in their stretch, naming both.
  - Store the address, never the quoted words, and keep the judgements in their own records pointing at it (stand-off annotation).
  - Text shown to a later act may be the stretches with their judgements applied (a reference followed to what it refers to), built by code from the addresses, so the source stays as written.
- **What would change our mind:** an act whose output is meant to be new prose (a summary, a briefing), where rewording is the work. It still cites the stretches it tells, by number.

## Stance: every call in use is kept, and a changed judge judges forward

- **Stance:** the running app keeps every model call it makes, the request exactly as sent and the response exactly as returned, for good and never rewritten, and each output points to the call that made it. The kept call names the output's judge (the act, its instructions' version, the model, the request's hash). Where the app keeps a model's judgements as its record, a new judge (another model, a new version of the instructions) judges what arrives from then on; the judgements made before stand, with their judge, and a view reads, for each thing judged, the newest judge that has judged it.
- **Why:** judgement is read in use (tier 3), and when feedback says an output is wrong, only the request as sent says why the act judged so: inputs assembled at run time (precedents, candidates drawn from the store as it stood) are reproduced by no commit. Re-judging the whole record on every change costs as much as the record is large, and it grows daily, for every instruction tried; judgements kept with their judge let every view say who judged what it shows, and let a change be tried without rewriting what is already in use.
- **How to apply:**
  - Keep thinking, refusals and answers the act's checks refused, with the reason. Kept calls are a side record: no act is shown them, since an act shown its own earlier answers takes instructions by another route.
  - Hash a kept call's request as recordings hash theirs (*a recording answers exactly one request*), so "the same request" means one thing in use and in the suite, and a call that went wrong is already a fixture's input where its material is admissible.
  - Keep the call's id with each output, or the piece of work that produced it: matching by time and work key breaks when one run handles many pieces of work at once.
  - "What arrives from then on" is bounded by a cutoff the switch records (items collected after it), never by a new step's own first-run timestamps. A migration or new step that changes what marks an item as new otherwise makes its first run see the whole backlog as new, and the next act is handed the record in one call, past every normal input and price step. Tests on fresh records can't see it; a priced dry run against the real record before the first live run can.
  - Re-judging a range is a deliberate run on the owner's say, priced first, as a re-recording is, and stops before it could pass the most it may spend.
  - A candidate judge is compared on the live record by re-judging a sample, kept beside the live judgements and read by no view until it is chosen. Choosing it is a recorded act of its own, on the model and version the act runs on from then.
  - Judgements address what they judge by something that never changes (*the model judges addresses into the source*), so no judgement or feedback is left pointing at nothing when a new judge judges differently.
- **What would change our mind:** a record small enough, or judges cheap enough, that re-judging all of it on each change costs nothing worth planning around.
